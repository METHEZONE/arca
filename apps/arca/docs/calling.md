# ARCA 통화 (ARCA↔ARCA)

## 왜 만들었나

아이폰에서 "상대방 고지 없이 + 에어팟 껴도 + 통화품질 안 깨지고" 전 통화를 녹음하는 방법은 **존재하지 않는다.** iOS는 `CallKit`이나 기본 전화 앱의 오디오에 접근하는 공개 API를 아예 제공하지 않고, 우회하는 앱은 심사에서 거절한다. 백그라운드로 마이크를 켜두는 우회도 막혀 있다 — 전화가 오면 iOS가 녹음을 강제 중단하고 자동 재개하지 않는다.

그래서 선택지는 두 갈래뿐이다.

| 방법 | 자동 | 무고지 | 품질 | 에어팟 | 비용 |
|---|---|---|---|---|---|
| SKT 에이닷 | O | O | mVoIP (약전계 취약) | O | 무료 |
| iOS 순정 녹음 | X | **X (고지 강제)** | VoLTE | O | 무료 |
| PLAUD Note | X (버튼) | O | VoLTE | **X** | 18만원 |
| PSTN 브릿지 (Twilio) | O | O | VoLTE | O | 월 5~8만원 |
| **ARCA 통화 (이 문서)** | **O** | **O** | **우리가 통제** | **O** | 릴레이 서버비만 |

마지막 줄이 유일하게 네 칸을 다 채운다. 이유는 단순하다: 오디오 그래프 전체가 우리 것이면 녹음은 그냥 파일 쓰기다. Zoom과 Discord가 통화를 녹음할 수 있는 것과 똑같은 이유이고, **App Store 정책 위반이 아니다.** 셀룰러 통화를 훔치는 게 아니라 자기 앱의 오디오를 저장하는 것이기 때문이다.

## 법적 전제

한국은 **본인이 당사자인 통화는 상대 동의 없이 녹음해도 합법**이다. 통신비밀보호법 제3조가 금지하는 것은 "공개되지 아니한 **타인간의** 대화"이고, 대법원은 당사자 일방의 녹음은 여기에 해당하지 않는다고 일관되게 판시했다 (2006도4981 등). 동의 없는 녹음을 처벌하는 개정안은 발의만 됐고 통과되지 않았다.

단, 녹음과 **공개**는 별개다. 대법원 2025다204730은 음성권을 인격권으로 인정했다 — 녹음 자체는 적법하지만 SNS 공개는 손해배상·명예훼손 책임이 붙을 수 있다. 법원 증거 제출은 문제없다.

## 설계

```
   iPhone A                     릴레이 (서울)                    iPhone B
 ┌──────────┐   WSS 시그널링   ┌──────────────┐  WSS 시그널링   ┌──────────┐
 │  ARCA    │◄────────────────►│  방 매칭     │◄───────────────►│  ARCA    │
 │          │   공개키만 전달  │  공개키 중계 │                 │          │
 │  Curve   │                  ├──────────────┤                 │  Curve   │
 │  25519   │   UDP (암호화)   │  UDP 포워딩  │   UDP (암호화)  │  25519   │
 │  ChaCha  │◄────────────────►│  복호화 불가 │◄───────────────►│  ChaCha  │
 └──────────┘                  └──────────────┘                 └──────────┘
```

**릴레이를 쓰는 이유.** 양쪽이 다 통신사 NAT 뒤의 휴대폰이라 홀 펀칭이 자주 실패한다. 그러면 ICE 전체 + TURN 폴백이 필요한데, TURN 자체가 결국 릴레이다. 예측 불가능한 경로 두 개보다 예측 가능한 경로 하나가 낫다. 서울에 두면 추가 홉이 5~20ms이고, 그 값은 HUD에 그대로 표시된다.

**릴레이는 통화를 들을 수 없다.** 미디어 키는 두 단말이 Curve25519 ECDH로 직접 유도한다(방 코드를 salt에 섞어 리플레이 방지). 시그널링 서버는 공개키만 본다. 패킷은 ChaChaPoly AEAD로 봉인되고, 릴레이는 라우팅 헤더만 읽고 나머지는 바이트 그대로 넘긴다.

### 품질을 만드는 요소

| 요소 | 선택 | 이유 |
|---|---|---|
| 코덱 | AAC-ELD 48kHz mono 40kbps | SDK에 있는 유일한 대화형 코덱. 알고리즘 지연 ~15ms (AAC-LC는 100ms+). **VoLTE의 AMR-WB는 16kHz 샘플링이라 대역폭 자체가 우리보다 좁다** |
| 에코/노이즈 | `setVoiceProcessingEnabled(true)` | FaceTime과 동일한 Apple VoiceProcessingIO. 직접 만들 수 없는 부분을 공짜로 얻는다 |
| 세션 모드 | `.playAndRecord` + `.voiceChat` | 통화 전용 입력 경로, 블루투스 HFP 유지, 시스템 덕킹 |
| 프레이밍 | 10ms 프레임, 2개/패킷 (20ms) | VoLTE와 같은 패킷화. 손실 피해 최소화 |
| 손실 보정 | 이중 전송 (FEC) | 모든 프레임을 두 패킷에 실어 보낸다. 80kbps로 올라가지만 **단일 패킷 손실이 들리지 않게 된다.** 모바일에서 가장 값싼 품질 개선 |
| 지터 버퍼 | 적응형 (`CallJitterBuffer`) | 고정 20ms는 Wi-Fi에서 완벽하고 LTE에서 찢어진다. 고정 200ms는 대화 턴테이킹을 망친다. 측정된 지터를 따라 움직인다 |
| 전송 | UDP + `serviceClass = .responsiveData` | 혼잡한 라디오에서 백그라운드 트래픽보다 앞서 큐잉되도록 OS에 요청 |
| 재생 | `AVAudioSourceNode` + lock-free 링버퍼 | 렌더 스레드에서 락을 잡으면 주기적 클릭이 생긴다 |

지터 버퍼가 체감 품질의 절반이다. 그래서 오디오·소켓 의존성 없는 순수 로직으로 분리해 단위 테스트를 붙였다 (`CallingTests.swift`).

## 파일 지도

```
Packages/ArcaVoiceKit/Sources/Calling/
  CallWire.swift          와이어 상수 + 패킷 바이너리 코덱 + 단조 시계
  CallCrypto.swift        ChaChaPoly 패킷 봉인, 방향별 nonce salt
  CallKeyExchange.swift   Curve25519 ECDH → HKDF → 미디어 키
  CallCodec.swift         AAC-ELD 인코드/디코드 (+ PCM 탈출구)
  CallJitterBuffer.swift  적응형 재생 버퍼 (순수 로직)
  CallQuality.swift       RTT/지터/손실 집계 + G.107 기반 MOS 추정
  CallRingBuffer.swift    SPSC lock-free 링버퍼
  CallAudioEngine.swift   전이중 오디오, VoiceProcessingIO
  CallRecorder.swift      me.m4a / them.m4a 분리 녹음
  CallTransport.swift     UDP 릴레이 소켓 + 킵얼라이브
  CallSignaling.swift     WebSocket 방 매칭
  CallMediaPipeline.swift 핫패스 오케스트레이션
  CallSession.swift       @MainActor 관찰 가능 상태 (UI용)

CallLab/                  품질 측정 전용 독립 앱 (본편 무수정)
services/call-relay/      시그널링 + UDP 릴레이 (Node)
```

**녹음이 두 트랙인 이유.** `me.m4a`와 `them.m4a`를 따로 쓰면 화자 분리가 공짜다. 클러스터링이 틀릴 일이 없다. 상대 패킷이 유실되면 그 자리에 무음을 채워 두 파일의 타임라인을 정렬한다.

## 릴레이 배포

서울에 두는 게 이 설계의 지연 예산 전부다.

```bash
cd services/call-relay
npm install
SIGNALING_PORT=8080 MEDIA_PORT=8081 npm start
node test/relay.test.mjs      # 9개 체크
```

- **추천 호스트**: Oracle Cloud `ap-seoul-1` always-free ARM 인스턴스. 이 프로세스는 코어 하나로 수백 통화를 처리한다. AWS `ap-northeast-2`도 무관.
- **Vercel은 불가**: UDP도 상시 WebSocket도 안 된다.
- 방화벽에서 TCP 8080(또는 443 리버스 프록시), **UDP 8081** 열 것.
- 시그널링은 반드시 `wss://` (TLS)로. 방 코드와 공개키가 여기로 흐른다.
- `GET /health` 로 방 개수 확인.

## 측정 방법

CallLab을 아이폰과 맥(또는 아이폰 두 대)에 올리고:

1. 설정에서 릴레이 호스트/포트, 시그널링 URL 입력
2. 한쪽 "생성"으로 방 코드 만들고 발신, 다른 쪽 같은 코드로 수신
3. HUD 숫자를 본다

읽는 법:

| 숫자 | 기준 |
|---|---|
| MOS | 4.0+ 일반 통화보다 나음 / 3.6+ 좋음 / 3.0 미만이 지지직 구간 |
| 손실률 | 2% 넘으면 귀에 들린다 |
| 편도 체감 지연 | 150ms 넘으면 대화가 겹치기 시작 |
| 버퍼 깊이 | 네트워크가 나쁠 때 알아서 깊어진다. 150ms 넘게 유지되면 회선이 나쁜 것 |
| 중복 수신 | 높아도 정상. FEC가 일하고 있다는 뜻 |
| 버퍼 고갈 | 0이 아니면 네트워크가 순간적으로 끊긴 것 |

**A/B 방법**: 같은 장소에서 에이닷으로 통화하고 체감을 기록한 뒤, 같은 자리에서 CallLab으로 통화해 MOS를 본다. 지하철·엘리베이터·이동 중을 반드시 포함할 것 — 에이닷이 무너지는 지점이 거기이고, 우리도 QoS 우선순위가 없어서 취약한 지점이 거기다.

품질이 나쁠 때 **설정에서 코덱을 PCM으로 바꿔** 다시 걸어보면 원인이 갈린다. PCM(약 770kbps, Wi-Fi 전용)에서도 나쁘면 회선 문제고, PCM에서 괜찮아지면 인코더 문제다.

## 정직한 한계

- **QoS 우선순위가 없다.** VoLTE는 국제표준(QCI)으로 무선 자원에서 최우선 처리된다. 우리 패킷은 일반 데이터와 섞인다. 약전계·혼잡 구간에서는 물리적으로 못 넘는 벽이다. `serviceClass`와 FEC로 완화할 뿐이다.
- **상대도 ARCA가 있어야 한다.** 이 단계는 ARCA↔ARCA 전용이다. 외부 번호로 확장하려면 070/SIP 게이트웨이가 필요하다 (한국 인터넷전화 이동통화료 분당 48~92원 수준).
- **CallKit/PushKit이 아직 없다.** 지금은 양쪽이 앱을 열고 방 코드를 넣어야 한다. 앱이 닫혀 있어도 전화처럼 울리게 하려면 PushKit VoIP 푸시 + CallKit이 필요하다. VoIP Services Certificate는 기존 Apple Developer 계정으로 발급 가능하다.
- **연락처/신원 개념이 없다.** 방 코드가 유일한 식별자다.

## 다음 단계

1. 품질 측정 (지금 여기)
2. 숫자가 납득되면 → CallKit + PushKit, 연락처 기반 발신, `Features/Call/`로 화면 이관

4. 그 다음이 070/SIP 게이트웨이 — 외부 번호까지 커버되면 모든 업무 통화가 자동 녹음된다
